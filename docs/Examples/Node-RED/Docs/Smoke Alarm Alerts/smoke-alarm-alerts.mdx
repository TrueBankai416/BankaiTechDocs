This example shows a Node-RED flow that watches a hardwired smoke and carbon monoxide (CO) detector, plus a battery powered listener that hears the detector's alarm, in Home Assistant. When any of them goes off, it sends a high priority phone notification and switches the living room lights to a fire alarm scene. When they clear, it sends a quieter notification and puts the lights back.

- **Alarm detected**: a loud, vibrating notification titled `🚨 FIRE/SMOKE ALARM DETECTED` (or `CARBON MONOXIDE`, or `SMOKE/CO` from the listener) with a red fire or CO icon in the status bar, and the lights switch to the fire alarm scene.
- **Alarm cleared**: a plain notification titled `✅ FIRE/SMOKE ALARM CLEARED` with a green check icon in the status bar, so it doesn't sound like another alarm. The lights go back to the natural light scene once every sensor is clear.
- **One notification per alarm**: the listener can't tell fire from CO, so it is only a backup. It notifies only if the ZEN55 doesn't report the alarm first, and it never repeats a ZEN55 notification.
- **One function node**: `Alarm Logic` handles every sensor, so the notifications and the lights always agree.
- **Test buttons**: four inject nodes simulate each alarm and clear without touching the real sensors or the lights.

## Prerequisites

- Node-RED with the [node-red-contrib-home-assistant-websocket](https://github.com/zachowj/node-red-contrib-home-assistant-websocket) palette installed (exported with version 0.82.0) and a configured Home Assistant server connection.
- A smoke and CO detector that exposes two binary sensors in Home Assistant. The export uses a hardwired Zooz ZEN55 with `binary_sensor.smoke_detector_smoke_detected` and `binary_sensor.smoke_detector_carbon_monoxide_detected`.
- A binary sensor that reports when the detector's alarm is sounding, without saying which kind. The export uses a battery powered alarm listener, `binary_sensor.alarm_listener_alarm_status`, which hears the detector but can't tell fire from CO.
- A notify service for your phones. The export uses `notify.notify`, which sends to every device with the Home Assistant mobile app.
- For the lights: the Philips Hue integration (the flow calls `hue.activate_scene`), the `light.living_room_switch` entity that powers the bulbs, and two Hue scenes: `scene.living_room_living_room_fire_alarm` and `scene.living_room_living_room_natural_light`.
- **Enable Global Context Store** turned on in the Home Assistant server node. The function reads the current state of the sensors and the light from it. The export has it on.

:::warning[This is not a replacement for your smoke alarm]
The alarm itself must still sound on its own. This flow only adds a phone notification and a lighting change. It depends on Node-RED, Home Assistant, your network, and your phone, and any of them can fail.
:::

## How it works

1. The `Alarm Sensors` node watches the two ZEN55 sensors (matched with the regex `binary_sensor.smoke_detector_(smoke_detected|carbon_monoxide_detected)$`) and the listener, and fires on each state change.
2. The `Alarm Logic` function node decides whether the change is an alarm or a clear. Anything else is dropped. It has two outputs.
3. Output 1 goes to `Notify User`, which sends the notification, and then to `Notification Log`, which shows the final message in the debug sidebar.
4. Output 2 goes to `Light Action`, which turns the lights on or activates a scene.

The sensors are listed at the top of the function:

| Sensor | Power | Label in notifications | Group | Role | Changes the lights |
| --- | --- | --- | --- | --- | --- |
| `binary_sensor.smoke_detector_smoke_detected` | Hardwired | FIRE/SMOKE | `fire` | Knows the alarm type | Yes |
| `binary_sensor.smoke_detector_carbon_monoxide_detected` | Hardwired | CARBON MONOXIDE | `co` | Knows the alarm type | Yes |
| `binary_sensor.alarm_listener_alarm_status` | Battery | SMOKE/CO | `listener` | Backup, can't tell fire from CO | Yes |

Sensors in the same group share one notification (see below). Set `lights: false` for a sensor in the `SOURCES` list if it should send notifications but leave the lights alone. A sensor that isn't in the list still works, with the label `UNKNOWN`, its own group, and changing the lights. A sensor with `backup: true` behaves like the listener.

| Sensor change | Notification | Lights |
| --- | --- | --- |
| A ZEN55 sensor → `on` (from `off`, `unavailable`, `unknown`, or no previous state) | **DETECTED**, high priority, unless another sensor in its group already raised the alarm | Fire alarm scene. If the light switch is off, it is turned on first |
| The listener → `on` | **DETECTED** only if no ZEN55 sensor is on after 5 seconds | Fire alarm scene right away |
| A ZEN55 sensor `on` → `off`, or `off` after an `unavailable` gap in the middle of an alarm | **CLEARED**, normal priority, once the last sensor in its group has cleared | Natural light scene, only if no other sensor is still on and the light is on |
| The listener → `off` | **CLEARED** only if the listener sent the alarm | Natural light scene, under the same conditions |
| Anything else, such as `on` → `unavailable` or `unavailable` → `off` with no alarm | Ignored | Nothing |

You get one notification per alarm, not one per sensor.

- **ZEN55 first, or at the same time:** the ZEN55 sensors know whether it's fire or CO, so their notification is the one you get. The listener stays quiet, and a pending listener notification is cancelled.
- **Listener first:** it waits `BACKUP_DELAY_MS` (5 seconds) for a ZEN55 sensor to report. If one does, you only get the ZEN55 notification. If none does, you get a `SMOKE/CO` notification, so you still hear about an alarm the ZEN55 missed.
- **ZEN55 reports after the listener notified:** you get the typed notification as well, because it tells you whether it's fire or CO.
- **The listener flaps:** if it goes off again before the delay ends, nothing is sent.
- **Smoke and CO together:** CO is in its own group, so it still notifies while a smoke alarm is active.

The lights always follow every sensor, including the listener, and go back to normal only when every sensor is clear.

To decide whether another sensor is still on, the function checks its current state in Home Assistant's global context. It also remembers which groups it has already notified, in node context. That memory is in the node, so it resets when Node-RED restarts, and the next alarm after a restart always notifies.

The function adds these properties to the message: `alarmType`, `alarmStatus`, `deviceName`, `timestamp`, `priority`, `title`, and `message`. It also writes the event to the Node-RED debug log with `node.warn`.

:::note[Why an alarm from `unavailable` still counts]
Z-Wave sensors can briefly show `unavailable` or `unknown` when the controller restarts or the device reconnects, and a battery powered sensor does this more often. If an alarm is reported right after that, the previous state isn't `off`. Checking only for `off` → `on` would drop that alarm silently, so any previous state other than `on` counts as a new alarm.
:::

:::note[Why the function remembers which sensors are on]
A battery powered sensor can go `unavailable` between `on` and `off`. A check for `on` → `off` would miss that clear, so the lights would never go back. The function keeps a list in node context of the sensors it reported as `on` and sends a clear when one of them reports `off`. The list is in memory, so it resets when Node-RED restarts.
:::

The function node code:

```js
// Output 1: notification. Output 2: light calls.
// Sensors in the same group share one notification.
const SOURCES = {
    'binary_sensor.smoke_detector_smoke_detected': { label: 'FIRE/SMOKE', group: 'fire', lights: true },
    'binary_sensor.smoke_detector_carbon_monoxide_detected': { label: 'CARBON MONOXIDE', group: 'co', lights: true },
    // Hears the detector but can't tell fire from CO, so it is only a backup
    'binary_sensor.alarm_listener_alarm_status': { label: 'SMOKE/CO', group: 'listener', lights: true, backup: true }
};
const LIGHT = 'light.living_room_switch';
const ALARM_SCENE = 'scene.living_room_living_room_fire_alarm';
const NORMAL_SCENE = 'scene.living_room_living_room_natural_light';
const POWER_ON_DELAY_MS = 2000; // time for the bulbs to connect after the switch turns on
const BACKUP_DELAY_MS = 5000;   // how long a backup sensor waits for a typed sensor to report first

const entity = msg.data && msg.data.entity_id;
const newState = msg.payload;
const oldState = msg.data && msg.data.old_state ? msg.data.old_state.state : null;
if (!entity || typeof newState !== 'string') {
    return null;
}
const source = SOURCES[entity] || { label: 'UNKNOWN', group: entity, lights: true };

const ha = global.get('homeassistant');
const states = ha?.homeAssistant?.states;
const call = (action, entityId) => ({ payload: { action, target: { entity_id: entityId } } });

const cancelTimer = () => {
    clearTimeout(context.get('lightTimer'));
    context.set('lightTimer', null);
};

// Alarm lights on. An unreadable light state counts as "on" so the scene still runs.
const lightsOn = () => {
    // A second sensor shouldn't restart a scene that is already waiting for the bulbs
    if (context.get('lightTimer')) {
        return null;
    }
    if (states?.[LIGHT]?.state !== 'off') {
        return call('hue.activate_scene', ALARM_SCENE);
    }
    node.send([null, call('light.turn_on', LIGHT)]);
    context.set('lightTimer', setTimeout(() => {
        context.set('lightTimer', null);
        node.send([null, call('hue.activate_scene', ALARM_SCENE)]);
    }, POWER_ON_DELAY_MS));
    return null;
};

// Is another sensor that matches the filter on right now, according to Home Assistant?
const othersOn = (match) => Object.keys(SOURCES).some((id) =>
    id !== entity && match(SOURCES[id]) && states?.[id]?.state === 'on');

// Back to normal, but only once every source that drives the lights is clear
const lightsRestore = () => {
    if (othersOn((s) => s.lights)) {
        return null;
    }
    cancelTimer();
    return states?.[LIGHT]?.state === 'on' ? call('hue.activate_scene', NORMAL_SCENE) : null;
};

// Sources reported as "on" that haven't cleared yet. This lets a clear through when
// a battery sensor goes unavailable between "on" and "off".
const active = context.get('active') || {};
// Groups that sent a DETECTED notification and haven't sent CLEARED yet
const notified = context.get('notified') || {};
const sameGroup = (s) => s.group === source.group;

// Is a sensor that knows the alarm type on right now? Reads the live state each time.
const typedSensorOn = () => {
    const live = global.get('homeassistant')?.homeAssistant?.states;
    return Object.keys(SOURCES).some((id) => !SOURCES[id].backup && live?.[id]?.state === 'on');
};

const cancelBackup = () => {
    clearTimeout(context.get('backupTimer'));
    context.set('backupTimer', null);
};

const notification = (status) => ({
    ...msg,
    alarmType: source.label,
    alarmStatus: status,
    deviceName: entity,
    timestamp: new Date().toISOString(),
    priority: status === 'DETECTED' ? 'high' : 'normal',
    title: (status === 'DETECTED' ? '🚨 ' : '✅ ') + source.label + ' ALARM ' + status,
    message: source.label + ' alarm ' + status.toLowerCase() + ' on ' + entity
});

let status;
let notify;
let lightMsg = null;

// Any previous state other than "on" counts, so an alarm that shows up right after
// a sensor was unavailable or unknown isn't missed.
if (newState === 'on' && oldState !== 'on') {
    status = 'DETECTED';
    active[entity] = true;
    if (source.backup) {
        // Notify only if no typed sensor reports the alarm within the delay
        notify = false;
        if (!typedSensorOn()) {
            cancelBackup();
            context.set('backupTimer', setTimeout(() => {
                context.set('backupTimer', null);
                if (typedSensorOn()) {
                    return;
                }
                context.set('notified', { ...context.get('notified'), [source.group]: true });
                node.warn(`${source.label} ALARM DETECTED: ${entity} changed from ${oldState} to ${newState}`);
                node.send([notification('DETECTED'), null]);
            }, BACKUP_DELAY_MS));
        }
    } else {
        // A typed sensor reported, so a pending backup notification is redundant
        cancelBackup();
        // Skip the notification if another sensor in the group already raised this alarm
        notify = !(notified[source.group] && othersOn(sameGroup));
        notified[source.group] = true;
    }
    if (source.lights && !msg.test) {
        lightMsg = lightsOn();
    }
} else if (newState === 'off' && (active[entity] || oldState === 'on')) {
    status = 'CLEARED';
    delete active[entity];
    if (source.backup) {
        // Only send a clear if the backup sensor actually sent the alarm
        cancelBackup();
        notify = Boolean(notified[source.group]);
    } else {
        // Wait for the last sensor in the group before sending the clear
        notify = !othersOn(sameGroup);
    }
    if (notify) {
        delete notified[source.group];
    }
    if (source.lights && !msg.test) {
        lightMsg = lightsRestore();
    }
} else {
    return null;
}
context.set('active', active);
context.set('notified', notified);

if (!notify) {
    return lightMsg ? [null, lightMsg] : null;
}

node.warn(`${source.label} ALARM ${status}: ${entity} changed from ${oldState} to ${newState}`);
return [notification(status), lightMsg];
```

## The notification

`Notify User` builds its data with a JSONata expression, which reads `title`, `message`, `alarmStatus`, and `alarmType` straight from the message:

```
{
  "title": title,
  "message": message,
  "data": alarmStatus = "DETECTED" ? {
    "priority": "high",
    "ttl": 0,
    "channel": "alarm",
    "importance": "high",
    "notification_icon": alarmType = "CARBON MONOXIDE" ? "mdi:molecule-co" : "mdi:fire",
    "color": "red",
    "vibrationPattern": "100,1000,100,1000,100"
  } : {
    "notification_icon": "mdi:check-circle",
    "color": "green"
  }
}
```

:::warning[`title` and `message` must be set on the message]
In JSONata, a field that doesn't exist on the message is silently left out. If the function doesn't set `msg.title` and `msg.message`, the notification has no message, and Home Assistant's `notify` service requires one, so the call fails. That is why the function sets both.
:::

The `data` options are for the Android Home Assistant app:

- **`priority: high` and `ttl: 0`**: deliver immediately, even when the phone is in a low power state.
- **`channel: alarm` and `importance: high`**: put alerts in their own notification channel. In the app's notification settings you can choose its sound and whether it overrides Do Not Disturb.
- **`vibrationPattern`**: a long, repeating vibration.
- **`notification_icon` and `color`**: the small icon in the status bar and at the top of the notification, tinted with the color. It isn't a picture inside the notification body. The 🚨 and ✅ in the title are plain emoji set by the function.

On iOS these Android options are ignored. For a critical alert there, add `push: { sound: { name: "default", critical: 1, volume: 1.0 } }` to the data. See the [Home Assistant companion app notification docs](https://companion.home-assistant.io/docs/notifications/notifications-basic/) for all the options.

## The lights

The function's second output sends a message that names the call: `msg.payload.action` is the service (`light.turn_on` or `hue.activate_scene`) and `msg.payload.target` holds the entity. `Light Action` has no action configured and **Block Input Overrides** off, so the message decides what it does. The older `domain` and `service` payload format still works in palette version 0.82.0, but it logs a deprecation warning.

A few behaviours to know:

- **Light timing:** a second sensor going off while the light switch is still powering on doesn't restart the 2 second wait, so the scene is applied once.
- **Light switch off:** the function turns the switch on, waits 2 seconds for the bulbs to connect, then activates the fire alarm scene.
- **Cancelled scene:** if the alarm clears during that 2 second wait, the pending fire alarm scene is cancelled, so it can't fire after the lights are restored.
- **Lights stay on:** the flow doesn't remember whether the lights were off before the alarm. After an alarm that started with the light off, it stays on with the natural light scene.
- **Restarts:** `Output on connect` is off on the `Alarm Sensors` node, so deploying or restarting Node-RED doesn't change the lights. If you turn it on, an alarm that is already active at startup triggers the scene, but every restart also restores the natural light scene.

## Testing

The four inject nodes (`Test Fire Alarm`, `Test CO Alarm`, `Test Fire Alarm Clear`, `Test CO Alarm Clear`) each feed a small function node that fakes the sensor event and sends it to `Alarm Logic`. The real sensors aren't touched, and the fake events set `msg.test`, which tells the function to skip the lights. The notifications are real and go to your phone. Warn your household before you test.

After you click one, check that:

- The phone notification has the right title and message, with 🚨 or ✅ in the title and the right icon in the status bar.
- The `Notification Log` debug output shows the message with its `title`, `message`, and `alarmStatus`.
- Clicking a `Clear` button sends a plain notification, not a loud one.

The test buttons only cover the ZEN55 sensors and don't test the lights or the listener. To test the lights without a real alarm, temporarily add a toggle helper to the `Alarm Sensors` node and switch it on and off. A sensor that isn't in the `SOURCES` list uses the `UNKNOWN` label and changes the lights. To test the listener path, add the helper to `SOURCES` with `backup: true`.

## Before importing

- Update the sensor names in the `Alarm Sensors` node and in the `SOURCES` list at the top of the function to match your own entities. The `Alarm Sensors` node and the function must list the same sensors. Give sensors that detect the same hazard the same `group`, and set `backup: true` on any sensor that can't tell which kind of alarm it heard.
- Update the light and scene entity IDs at the top of the function.
- Replace `notify.notify` with your own mobile app notify service if you only want specific phones alerted.
- The flow doesn't alert when a sensor goes `unavailable`, which can mean a dead battery or a lost connection, especially on the battery powered listener. Consider adding a separate notification for that.
